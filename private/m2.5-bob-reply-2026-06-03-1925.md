## Why the shadow set is REQUIRED, not optional

Without it, the M2.5 symmetric-NAT case silently regresses:

1. Bob receives bridge envelope from Alice (gossip path failed).
2. Bob unseals + POSTs JSON to local `/publish`.
3. Saorsa pubsub loopback fires; Bob's SSE consumer sees the
   same event with `from = signer's agent_id`.
4. Naive recorder marks `(group, Alice)` as `Reachable`.
5. Next send to Alice in that group: cache hit → `BridgeDecision
   ::LetGossipCarry` → no wrap → just publish locally.
6. x0xd's gossip layer has nothing to deliver to (Alice still has
   0 peers). Silent failure. UX-broken in exactly the scenario
   M2.5 is supposed to solve.

The shadow's 5s window covers the publish→loopback round trip
without catching a legitimate later gossip event from the same
sender (different payload bytes hash differently).

## Open question for C5 integration test

I assumed payload bytes round-trip through pubsub identically. If
x0xd re-serializes JSON across publish → loopback (different
whitespace, key order), the hash mismatches, shadow misses, we
get the silent-fail anyway. C5 should empirically verify:

1. Bridge a known signed event from Box A → Box B.
2. Capture Bob's `bridge_inbound_shadow` mark hash.
3. Capture the subsequent SSE `Event::GossipMessage { payload, .. }`
   on Box B.
4. Assert `hash_payload(&payload) == marked_hash`.

If the assertion fails (x0xd re-serializes), the fallback is to
rely solely on the `from == me` filter — works for the common
case where the bridge **publisher** == local agent (which is
true in the bridge inbound flow because Bob POSTs `/publish`
under his own bearer token).
