## Chat -- delivery and reliability

- Per-message delivery state **Sending / Delivered / Not delivered**: recipient emits `EnvelopeKind::DeliveryReceipt` via `build_receipt_outbox` (`crates/fetchit-chat/src/conversation/outbound.rs:225`), sender binds it with `Conversation::apply_delivery_receipt` (`conversation/types.rs:291`), desktop UI is `BubbleStatusTag` (`apps/fetchit-desktop/src/chat/bubble.ts:249`).
- **DM resend / engine-owned outbox** (the client carries retention past the relay's 15-min TTL): an offline->online edge re-sends in-flight/failed bubbles, a 24h sweep flips stuck sends to an honest "failed", survives app restart, double-send-guarded. Lives in the shared engine -- `crates/fetchit-chat/src/outbox/{mod,store,driver}.rs` (`OutboxStore`, presence-driven `OutboxDriver`), driven by `Client::enqueue_dm` / `start_outbox_driver` / `retry_outbox`, so BOTH shells share one loop: desktop projects each `OutboxEvent` via `ChatStore.applyOutboxEvent` (`apps/fetchit-desktop/src/chat/state.ts`), Android via the FFI outbox surface + `ConversationStore.upsertOutbox`. A `DeliveryReceipt` marks the durable bubble Delivered engine-side through `conversation::dispatch_inbound_with_outbox`, so a delivered DM is never re-sent.
- **Private-group send durability** (the same client-carried retention extended to group fan-out; reverses the outbox-lift DM-only scope): a private-group send whose fanout reaches no member (relay down) no longer hard-fails. `Endpoint::send_private_group` (`crates/fetchit-chat/src/messages.rs`) enqueues one retryable outbox bubble per undelivered member -- each carrying the once-sealed frame as postcard bytes (`outbox/mod.rs` `GroupOutbound`) -- and returns Ok so the sender sees the message. The presence-driven `OutboxDriver` re-sends each stored frame verbatim on reconnect via `RealOutboxTransport` -> `Endpoint::resend_group_bubble`, NEVER re-sealing (`TreeKEM` ratchets, so a re-seal would duplicate at the receiver). A relay-accepted group resend is terminal (`OutboxStatus::Delivered`) because groups get no per-member `DeliveryReceipt`, so it never re-fires. Prod-wired via the `Endpoint` outbox sink in `Client::messages`; a `None` sink (tests / REST-only) keeps the pre-durability hard-fail.
- Relay **transit buffer** (RAM-only, hard 15-min TTL, fire-and-forget), drained on every WS reconnect -- `crates/fetchit-relay-server/src/transit.rs:37` (`TransitBuffer`, `drain` at :83); replay at connect in `crates/fetchit-relay-server/src/ws.rs:94` (`replay_transit` at :398). No cursor/since/inbox query; DM catch-up is implicit on reconnect.
- Per-group **bridge consent** (default-off, per-group opt-in), encrypted at rest and persisted across restart -- `crates/fetchit-chat/src/groups_reachability.rs:144` (`BridgeConsentStore`; `load` / `flush` seal the map to `bridge/consent.json.enc` via `at_rest::seal_to_path`, fail-safe to empty on a damaged file). The prod `Client` ctor loads it; `new()` stays in-memory.
- Direct-gossip **reachability cache** (60s window, rebuilt from live gossip after restart) -- `crates/fetchit-chat/src/groups_reachability.rs` (`ReachabilityCache`, `STALE_AFTER_MS`).

## Chat -- transport and groups

- Message **content routing by reachability** (relay = Always, LAN-direct = IfReachable, future WebRTC = cross-NAT) -- `crates/fetchit-chat/src/transport/mod.rs` (`Router`, `Reachability`).
- Group **MLS control-plane** (Welcome/Commit/member changes) rides x0xd gossip as PRIMARY, relay only as a cross-NAT contingency -- `crates/fetchit-chat/src/transport/mod.rs` (does NOT use the `Router`).
- Forward-compat envelopes: the relay routes opaquely by `to` (`SendFrame.envelope_bytes`) and peers round-trip unrecognized kinds (`EnvelopeKind::Unknown(u8)`) -- `crates/fetchit-relay-proto/src/envelope.rs`.
- Private-group **decrypt works without prior per-sender DM pairing** (Option B): `Endpoint::receive_private_group_envelope` (`crates/fetchit-chat/src/messages.rs`) ML-DSA-verifies the sender against their stored card, then x0xd `/secure/decrypt`. An un-paired sender's signing key is resolved on the fly from the relay pair-record (`crate::pair::fetch_pair_record_by_id`; `verify_pair_record` in `crates/fetchit-relay-proto/src/pair_record.rs` binds `agent_id == SHA-256(domain || ml_dsa_pubkey)`, so a hostile relay cannot forge it) and persisted via `StoredContactCard::save_imported` (merge-floor, never downgrades a fuller card). Resolution runs as a join-time prefetch off the converged roster plus an on-receive lazy fetch, guarded by a 60s-TTL negative cache (`NEG_CACHE_TTL`) because RAM-only per-relay pair-records mean a 404 self-heals. NOTE: private-group **send** routing (MLS vs SignedPublic) is the in-progress `send_to_group` work, not yet landed.

## Chat -- linked-device DM fanout (M6.3)

- **A DM fans out to a contact's linked devices**: to an M6 contact (whose imported card carried an x0x `user_id`), `Endpoint::send` resolves their signed device list and seals one copy per device -- every linked device receives it, sharing one `message_id` for receive-side dedup, with no primary-device-online dependency (model A receive-fanout, complementary to the future M6.6 devices-group, not a substitute). `fanout_targets` -> `fanout_targets_from_record` (`crates/fetchit-chat/src/messages.rs`). A sibling device discovered only from the signed record (never imported as a contact, so no stored card) is bootstrapped straight from its user-signed `DeviceEntryV4` via `bootstrap_from_device` (record KEM); `bootstrap_conversation` (stored card) is the single-device fallback. Delivery is best-effort per device (one device's failure never aborts the rest), and the outbound `HistoryEntry` is anchored once on the `to`-agent conversation, so a multi-device contact stays exactly one sidebar thread.
- **Confidentiality gate (anti-redirection)**: `fanout_targets_from_record` trusts the resolved device list ONLY when `to` is one of the listed devices, else single-device fallback. The card `user_id` is only an AGENT-asserted claim (the x0x `AgentCard` carries no user-signed cert; `verify_card_extension` covers only the fetchit KEM/agent extension), so without the gate a spoofed card (`agent=Mallory, user_id=Victim`) would seal the DM to the victim's devices. The `PairRecordV4` USER signature covers each device's `agent_id_hex` (`pair_record_v4_signing_input`, `crates/fetchit-relay-proto/src/pair_record.rs`), so `to`-in-devices proves the account signed `to` as its own. Trust model in `crates/fetchit-chat/SECURITY.md` caveat 10.
- **Contact device-list read side**: `contact_user_id_hex` surfaces the peer's account root from their stored card; `resolve_pair_record_v4` GETs + verifies their signed device list from the contact's own relay with strictly-monotonic anti-rollback against a per-contact cache (`crates/fetchit-chat/src/pair_record_v4.rs`); a newer revision that revoked a device cancels that device's pending outbox sends (`removed_device_agents` + `OutboxStore::drop_bubbles_for_peers`, `crates/fetchit-chat/src/outbox/store.rs`).

## Chat -- proactive pair-record push (M6.7 send/receive)

- **A device-set change pushes the re-signed roster to active contacts** instead of making them wait to re-resolve: `Client::push_pair_record_to_active_contacts` (`crates/fetchit-chat/src/client.rs`) enumerates the distinct active peer devices across every cached conversation (`pair_record_push_recipients` over `Conversation::fanout_devices`, which drops our own device + revoked devices; cross-conversation duplicates collapsed) and sends each one an unsealed `PairRecordPush`. The push rides an `OutboundKind::Dm`-shaped envelope whose transit `kind` stays `EnvelopeKind::PairRecordPush`, so the relay forwards it (LAN drops it) and the receiver re-discriminates on `transit.kind`. Best-effort per recipient; the return count is the recipients the router accepted.
- **Receive is authority-gated, not sender-trusted**: the push is public + self-signed, so `Client::dispatch_inbound_pair_record_push` (`crates/fetchit-chat/src/client.rs`) ignores a push from a non-contact (`contact_user_id_hex` must resolve the sender's x0x `user_id`), then `accept_pushed_pair_record_v4` (`crates/fetchit-chat/src/pair_record_v4.rs`) accepts ONLY when `record.user_id_hex == expected && verify_pair_record_v4(record).is_ok() && record.revision > last_seen` (the record's own ML-DSA-65 user signature + strict anti-rollback are the sole authority). On accept over an existing record, the devices the new revision revoked have their pending outbox sends cancelled (`removed_device_agents` + `OutboxStore::drop_bubbles_for_peers`), mirroring the M6.3 resolve cleanup. The wire is unsealed by design (`crates/fetchit-relay-proto/src/pair_record_push.rs`, WIRE_VERSION 3). NOTE: the automatic trigger on a LOCAL device-set change (the revoke orchestration that calls `revoke_device_and_publish` -> devices-group `DevicesGroupSink::remove_device` -> this push) converges with the M6.6 devices-group and is not yet wired.

## Chat -- cross-NAT group-join (engine A)

- **Gossip-independent PQ TreeKEM group-join over the relay** (engine A): a NAT'd joiner converges into a group whose owner is also NAT'd, with no gossip/mDNS -- the FALLBACK for the dual-NAT corner where gossip can't reach a NAT'd owner (native x0x groups + gossip is the PRIMARY group path; gossip ships ON). Forward path -- the joiner's signed `member_joined` is bridged sealed to the owner, which applies it through `apply_metadata_event` (full ML-DSA + single-use invite + inviter gate) and publishes the authoritative `MemberAdded` -- `crates/fetchit-chat/src/client.rs:2170` (`join_group_bridged`), `crates/fetchit-chat/src/client.rs:1871` (`dispatch_inbound_bridge` forward arm), `crates/x0xd-client/src/secure.rs:574` (`apply_metadata_event`).
- Reverse path -- the owner bridges the `MemberAdded` back sealed; the joiner self-detects it and applies it locally so its TreeKEM membership poll resolves -- `crates/fetchit-chat/src/client.rs:2012` (`reply_to_bridged_join`), `crates/fetchit-chat/src/groups/join_bridge.rs:92` (`member_added_self_target`) + `:77` (`stable_group_id_from_member_joined`), `crates/x0xd-client/src/secure.rs:631` (`apply_join_result`). The joiner daemon gates the applied event to MemberAdded-only, `member == self`, `sender == creator`, and re-verifies the signed commit (wiremock-tested 200/409/403 in `secure.rs`).

## Chat -- identity (backup, restore, unification)

- **Seed-first identity + 24-word recovery phrase**: a fresh local-signer vault mints from a persisted 32-byte seed (`crates/fetchit-chat/src/local_signer.rs` `LocalSignerVault::load_or_create`, seed in `identity_seed_b64`); the seed round-trips as a BIP39 24-word phrase with checksum (`crates/fetchit-chat/src/recovery_phrase.rs` `seed_to_recovery_phrase` / `recovery_phrase_to_seed`). Legacy vaults (pre-seed) reveal `None` and must rotate to gain a backup.
- **Reveal**: `reveal_local_signer_recovery_phrase(data_dir, passphrase: Option)` (`local_signer.rs`; `None` = OS-keychain custody). FFI: `reveal_recovery_phrase` free fn (`crates/fetchit-ffi/src/chat_ffi.rs`); desktop command `chat_reveal_recovery_phrase` (`apps/fetchit-desktop/src-tauri/src/chat.rs`); desktop UI Settings > Identity backup, two-step reveal (`apps/fetchit-desktop/src/settingsBackup.ts`).
- **Restore**: `restore_identity_from_recovery_phrase` (`crates/fetchit-chat/src/client.rs`) reproduces the exact ML-DSA agent id via `from_seed`; REFUSES to overwrite an existing vault (`LocalSignerVault::restore_from_seed`). ML-KEM regenerates fresh; history does not restore. Platform discards a provably-virgin identity first (`discard_local_identity`), gated to first-run: FFI `restore_recovery_phrase`; desktop `chat_restore_recovery_phrase` + relaunch via `restart_app`; onboarding restore form (`apps/fetchit-desktop/src/onboarding/welcome.ts` `mountRestore`).
- **Identity unification, spawned daemon** (desktop): `seed_x0xd_agent_key(data_dir, passphrase, identity_dir)` (`crates/fetchit-chat/src/x0xd_seed.rs`) writes the vault keypair as `identity_dir/agent.key` in upstream x0x's bincode format (layout pinned by test against the bundled daemon; bump with the daemon, like the ant-core pin); desktop setup seeds before the supervisor spawns and the bundled TOML pins `identity_dir` (`apps/fetchit-desktop/src-tauri/src/lib.rs` `bundled_x0xd_toml_path`, appended for pre-unification installs). The embedded (Android) equivalent seeds in `ChatClient::connect` (`crates/fetchit-ffi/src/chat_ffi.rs`). Android backup/restore UI: Bob's lane, in progress.

## Fediverse bridge (M4 / M5.1)

- HTTP Signatures use **classical RSA-2048 + PKCS#1 v1.5 + SHA-256** (`rsa-v1_5-sha256`), NOT Ed25519 and NOT post-quantum -- `crates/fetchit-fedi/src/signature.rs`. The PQ binding is the ML-DSA-65 attestation in the Actor JSON-LD, not the per-POST signature. Crypto source of truth: `docs/honest-claims-crypto.md` §3.
- **One-tap mint (minimal profile)**: a fresh identity with no etch/it-published profile can still mint a fediverse handle. When the relay has no profile-index record (404 / tombstoned), `Client::mint_and_register_actor` (`crates/fetchit-chat/src/client.rs`) publishes a minimal handle-only record via `Client::publish_minimal_profile` -> `pair::sign_minimal_index_record` (`crates/fetchit-chat/src/pair.rs`): a self-signed `ProfileIndexRecord` carrying the reserved `pair::MINIMAL_PROFILE_ADDR` sentinel (not the all-zeros tombstone), POSTed to `{relay}/v1/profile`, no wallet / no Autonomi write. Only a genuine 404/tombstone triggers it -- an existing real profile is used and never clobbered; a transient relay error propagates. Both shells route through this one path: desktop `fediverse_mint` (`apps/fetchit-desktop/src-tauri/src/fediverse.rs`), the mobile FFI `fediMint` (no FFI API change -- one-tap on a `.so` rebuild). The rich profile stays an optional etch/it upgrade (same-`agent_id`, not a takeover).

## Shells

- **Desktop** (Tauri 2): full reader plus the chat/relay/trust stack -- entry `apps/fetchit-desktop/src/controller.ts`, render dispatch `apps/fetchit-desktop/src/renderers/dispatch.ts`, backend `apps/fetchit-desktop/src-tauri/`.

- **DM catch-up:** desktop replays the relay transit buffer on reconnect; the Android chat shell shares the engine DM outbox (resend/retry), with inbound catch-up reviewed on the android-lit merge.
- **Desktop private-group receive + render:** `handle_inbound` (`apps/fetchit-desktop/src-tauri/src/chat.rs`) routes an inbound `PrivateGroupChat` envelope to `receive_private_group_envelope` and emits `chat:group-message`; the frontend `ChatStore.appendGroupMessage` (`apps/fetchit-desktop/src/chat/state.ts`) renders it in the group conversation via the `chat:group-message` listener (`apps/fetchit-desktop/src/chat/events.ts`). (Desktop private-group SEND is the in-progress `send_to_group` wiring.)
- **Desktop rendered-content sandbox ENFORCEMENT e2e** (proves the boundary DENIES, not just that the attributes are set): a WebdriverIO spec drives the real `WebKitWebDriver` against a hostile fixture that probes every escape vector from inside the rendered iframe -- Tauri IPC reach, neutered WebRTC/geo/sendBeacon/serviceWorker, DOM storage, host frame, `window.open`, egress -- and asserts each is denied. Spec `apps/fetchit-desktop/e2e/sandbox-enforce.spec.mjs`, fixture `apps/fetchit-desktop/src-tauri/src/e2e.rs` (`HOSTILE_ADDR`), boundary `apps/fetchit-desktop/src/renderers/htmlRewriter.ts`. Run: `cd apps/fetchit-desktop && xvfb-run -a npm run e2e` (needs `webkit2gtk-driver` + `xvfb` + `tauri-driver`).
