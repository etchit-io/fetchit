## Chat -- delivery and reliability

- Per-message **send-state truth** (`crates/fetchit-chat/src/send_state.rs`, `SendState`): **queued** (in the durable outbox, retried indefinitely -- a dropped socket or a lost transport ack NEVER reads as failure), **sent** (a relay acked durable acceptance; the only transition into it), **delivered** (recipient emits `EnvelopeKind::DeliveryReceipt` via `build_receipt_outbox` (`crates/fetchit-chat/src/conversation/outbound.rs:225`), sender binds it with `Conversation::apply_delivery_receipt` (`conversation/types.rs`) and `OutboxStore::mark_delivered`, which also matches ids superseded by a resend), **failed** -- terminal ONLY for verdicts no retry can change (`SendFailure::classify`: `ChatError::Denied` / `DeniedActor` / `SealedRequired`). State + its transition timestamp are persisted on both the outbox bubble and the `HistoryEntry`, exposed over uniffi as `SendStateFfi` + `state_changed_at_ms` on `OutboxBubbleFfi` / `ChatHistoryMessageFfi`, and folded together at listing time by `outbox::overlay::overlay_history_send_state` (a message is only as far along as its least advanced copy). Desktop UI is `BubbleStatusTag` (`apps/fetchit-desktop/src/chat/bubble.ts:249`).
- **DM resend / engine-owned outbox** (the client carries retention past the relay's 72 h transit TTL): an offline->online edge re-sends every retryable bubble, a periodic sweep releases send claims stalled past `driver::STALLED_CLAIM_MS` (a claim timeout, never a delivery deadline -- no sweep declares a message failed), survives app restart, double-send-guarded by the in-flight claim that every send path (initial send included) holds. Lives in the shared engine -- `crates/fetchit-chat/src/outbox/{mod,store,driver}.rs` (`OutboxStore`, presence-driven `OutboxDriver`), driven by `Client::enqueue_dm` / `start_outbox_driver` / `retry_outbox`, so BOTH shells share one loop: desktop projects each `OutboxEvent` via `ChatStore.applyOutboxEvent` (`apps/fetchit-desktop/src/chat/state.ts`), Android via the FFI outbox surface + `ConversationStore.upsertOutbox`. A `DeliveryReceipt` marks the durable bubble Delivered engine-side through `conversation::dispatch_inbound_with_outbox`, so a delivered DM is never re-sent.
- **Private-group send durability** (the same client-carried retention extended to group fan-out; reverses the outbox-lift DM-only scope): a private-group send whose fanout reaches no member (relay down) no longer hard-fails. `Endpoint::send_private_group` (`crates/fetchit-chat/src/messages.rs`) enqueues one retryable outbox bubble per undelivered member -- each carrying the once-sealed frame as postcard bytes (`outbox/mod.rs` `GroupOutbound`) -- and returns Ok so the sender sees the message. The presence-driven `OutboxDriver` re-sends each stored frame verbatim on reconnect via `RealOutboxTransport` -> `Endpoint::resend_group_bubble`, NEVER re-sealing (`TreeKEM` ratchets, so a re-seal would duplicate at the receiver). A relay-accepted group copy reaches `SendState::Sent` and stops there -- groups get no per-member `DeliveryReceipt`, so it is never re-fired (a re-send would duplicate at the receiver) and never claims delivery. Prod-wired via the `Endpoint` outbox sink in `Client::messages`; a `None` sink (tests / REST-only) keeps the pre-durability hard-fail.
- Relay **transit buffer with at-least-once delivery** (72h TTL, per-recipient count cap + global byte cap): EVERY addressed envelope is stored before it is pushed, whether or not the recipient has a live session, and replayed NON-destructively on every WS connect, each `Deliver` carrying its durable store id in `transit_seq`; the relay reclaims an entry only when the client echoes that id in a `ClientFrame::TransitAck` (delete is scoped to the authenticated agent, so a client can only ack its own backlog). Delivery to a socket is therefore PROVISIONAL -- a Cloudflare-idle-killed socket still accepts writes, so a push is not receipt (#327) -- and a socket that dies mid-push or mid-replay redelivers on the next connect instead of losing the envelope. `fetchit_relay_envelopes_pushed_total` counts the provisional hand-off, `fetchit_relay_envelopes_delivered_total` counts acks; one session replays at most `REPLAY_BATCH_MAX` entries (`ws.rs`) so a never-acking client cannot be made to push an unbounded batch. Store surface: `crates/fetchit-relay-server/src/transit.rs` (`TransitStore` trait -- `enqueue`/`read_all`/`delete`; in-RAM `TransitBuffer` default) plus the durable `SqliteTransitStore` (`transit_sqlite.rs`), operator-selected via `FETCHIT_RELAY_TRANSIT_DB` (config `transit_db_path` -> `Server::with_transit_store`; restart-survival proven in `tests/handshake.rs` `buffered_envelope_survives_server_restart_with_sqlite_store`); replay + ack handling in `crates/fetchit-relay-server/src/ws.rs` (`replay_transit`, `TransitAck` arm of `handle_client_frame`); end-to-end proof `crates/fetchit-relay-server/tests/handshake.rs` (`unacked_delivery_replays_on_reconnect_until_acked`, `live_delivery_stays_in_transit_until_acked`, `acked_live_delivery_is_reclaimed_and_not_replayed`). Client ack surface: `Client::ack_transit` (fire-and-forget, drops the `0` no-ack sentinel; `crates/fetchit-relay-client/src/client.rs`) and the routed `RelaySet::ack_transit(relay, ids)` fed by `RelaySet::next_delivery_tagged` (`relay_set.rs` `SetDelivery` -- ids are relay-local, so acks route to exactly the delivering relay, never broadcast); full loop proven in `crates/fetchit-relay-client/tests/end_to_end.rs` (`ack_transit_stops_redelivery_across_reconnects`). Engine ack-after-persist closes the loop: the relay pump attaches a one-shot `DeliveryAck` to each durable replay (`crates/fetchit-chat/src/transport/mod.rs`, wired in `relay_transport.rs` `spawn_inbound_pump`), and every consumer loop (engine `Client::default_dispatch_one`, peer, desktop src-tauri pump, FFI pump) confirms it ONLY at terminal outcomes -- vault-persisted, provable duplicate, or a deterministic verdict on immutable bytes -- per the `conversation::confirms_delivery` classifier. `StaleEpoch`/`KemDecapFailed`/missing-card frames hold the token, so the relay redelivers them within TTL and recovery (re-key, epoch catch-up) receives the frames again; duplicates on redelivery are absorbed by the inbound replay guard. No cursor/since query; DM catch-up is implicit on reconnect.
- Relay **durable per-group log** (serve-to-many, NOT delete-on-ack; serves epoch catch-up, durable join-result re-staging, and cold group reconstruction): `ClientFrame::LogAppend` deposits an opaque record (`Commit` recipient-less; `JoinResult` addressed to one joiner) onto a per-group append-only log, the relay assigning a monotonic per-group seq that starts at 1 and is never reused (the per-group watermark survives sweeps, evictions, and restarts). `ClientFrame::LogFetch { group_id, since_seq }` streams `ServerFrame::LogRecords` chunks of at most 64 records, final frame `done=true`; possession of the group id is the fetch capability for commits (the relay stays blind -- no membership check), while a `JoinResult` is served ONLY to the authenticated agent it addresses (`crates/fetchit-relay-server/src/ws.rs` `handle_log_fetch` / `handle_log_append`; deposits ride the Send arm's size cap + per-sender rate limiter, fire-and-forget with `Throttle` on cap rejection). Retention: 30-day window swept by the server sweeper + per-group cap 4096 evict-oldest-in-group + global 1 GiB byte cap reject (`config.rs` `group_log_window` / `group_log_per_group_cap` / `group_log_total_bytes_cap`). Store surface: `crates/fetchit-relay-server/src/group_log.rs` (`GroupLogStore` trait; in-RAM `RamGroupLog` default) plus the durable `SqliteGroupLog` (`group_log_sqlite.rs`) sharing the one `FETCHIT_RELAY_TRANSIT_DB` file with the transit store; restart survival proven in `tests/handshake.rs` `group_log_survives_server_restart_with_sqlite_store`, recipient gating in `join_result_served_only_to_its_addressed_agent`. Wire frames: `crates/fetchit-relay-proto/src/frame.rs` (`LogAppend` / `LogFetch` / `LogRecords`, appended last for postcard wire-compat). **Record provenance:** the relay stamps each stored record with the appending agent (`StoredLogRecord.author`, surfaced as `LogRecordWire.author`) taken from the authenticated session, never from the client -- `LogAppend` carries no author field, so it is structurally unforgeable (`ws.rs` `handle_log_append` passes `auth.agent_id`; proven end-to-end in `tests/handshake.rs` `group_log_stamps_each_record_with_its_authenticated_appender`). This is PROVENANCE, NOT AUTHORITY: a consumer must authorize against the ML-DSA-verified `committed_by` inside the payload. Payloads stay opaque, but the relay does now persist which agent appended each record (`author BLOB` column; pre-existing databases are migrated in place by an idempotent `ALTER TABLE`, and their older rows read back as `None`). The chat engine issues `LogFetch` over this log for warm epoch-recovery (the warm-recovery entry below); unsolicited `LogRecords` outside a fetch are still dropped by the supervisor reader. Producer side: the owner's join-reply path (`Client::reply_to_bridged_join`, `crates/fetchit-chat/src/client.rs`) deposits durable-first -- BEFORE the live sends -- via `groups::group_log::join_reply_log_intents` (`crates/fetchit-chat/src/groups/group_log.rs`): the Welcome-bearing event as a recipient-gated `JoinResult` and its commit-only projection as a broadcast `Commit`; best-effort, a log failure never blocks the live reply. The moderation dispatchers (`groups/dispatch.rs`) have no production callers yet and so do not append; wiring their append rides whichever change wires them (task: surface group moderation).
- Per-group **bridge consent** (default-off, per-group opt-in), encrypted at rest and persisted across restart -- `crates/fetchit-chat/src/groups_reachability.rs:144` (`BridgeConsentStore`; `load` / `flush` seal the map to `bridge/consent.json.enc` via `at_rest::seal_to_path`, fail-safe to empty on a damaged file). The prod `Client` ctor loads it; `new()` stays in-memory.
- Direct-gossip **reachability cache** (60s window, rebuilt from live gossip after restart) -- `crates/fetchit-chat/src/groups_reachability.rs` (`ReachabilityCache`, `STALE_AFTER_MS`).
- **The DM denylist gate covers every DEVICE, not just the conversation anchor** (`#342`): `Endpoint::send` gated only `to`, then `fanout_targets` expanded that one agent into every device on the recipient's `PairRecordV4` -- each a separately blockable agent id -- and sealed a copy for all of them, so a denylisted device kept receiving every message sent to its siblings. `retain_undenylisted_targets` (`crates/fetchit-chat/src/messages.rs`) filters the EXPANDED set (keeping `fanout_targets` purely about the device fabric), logs each skip at debug (steady state after a block, not an anomaly), and an expansion filtered to nothing raises the same `ChatError::Denied` the anchor check raises -- reachable when a poll-loop refresh lands between the two awaits, which is exactly the case that must not leak a sealed copy. Fail-open with no denylist wired.
- **Missed-message (gap) DETECTION for private groups**: each group send seals a per-sender monotonic counter inside the encrypted frame (`GroupBodyV1::seq`, relay-blind; allocated optimistically in `Endpoint::send_private_group`, `crates/fetchit-chat/src/messages.rs`); the receive path records it in the same locked mutation as the replay window (`Conversation::record_group_seq` -> `SenderSeqState`, `crates/fetchit-chat/src/conversation/seq_gap.rs`) and a counter jump surfaces as `GapReport` on `PrivateGroupReceive::Persisted` -- desktop emits `chat:group-gap` (`apps/fetchit-desktop/src-tauri/src/chat.rs`), peer bin logs a count-only anchor. Failure direction: duplicate/backward counters are absorbed, never a false alarm; holes bounded at `MISSING_CAP` (128) per sender with a `stale_missing` reorder-grace accessor. DETECTION ONLY -- recovery (catch-up re-fetch), the desktop UI affordance, and the Android FFI gap event are not built.
- **Warm epoch-recovery (fetch + apply)** (`#297` Lane A): a group member behind the MLS epoch catches up by pulling durable group-log records past its cursor and applying each through x0xd's signature-verifying endpoints -- never a bypass. `Client::recover_group_once` (`crates/fetchit-chat/src/client.rs`) drives the single recovery path that the warm, cold, and wedge triggers all funnel through; the warm seams are `LogFetchCommitSource` (`crates/fetchit-chat/src/groups/epoch_recovery/log_source.rs` -- issues `RelayTransport::log_fetch`, maps `LogRecordWire` -> `CommitRecord` via `wire_map::commit_record_from_wire`: base64 payload + hex author) and `X0xdCommitApplier` (`log_applier.rs` -- routes each record via the pure `wire_map::plan_apply` to `apply_metadata_event` for a commit / `apply_join_result` for a self-addressed `MemberAdded`, mapping the daemon's 200/409 to `Applied`/`AlreadyApplied`; the daemon re-runs full membership authority, so the relay-stamped author is a routing hint only, and a forged record is rejected daemon-side rather than applied). Passthroughs added: `RelaySet` / `RelayTransport::log_fetch` + `log_append` (`crates/fetchit-relay-client/src/relay_set.rs`, `crates/fetchit-chat/src/relay_transport.rs`), targeting the primary relay (index 0) so the single non-durable cursor tracks one coherent seq space. No relay configured -> empty fetch -> cold pending-join fallback, never a false `Live`. Covered by wiremock apply-endpoint tests (`log_applier.rs`), relay-round-trip source tests (`log_source.rs`), pure routing tests (`wire_map.rs`), and producer-intent tests (`groups/group_log.rs`). Producer half: the owner join-reply deposits both records durable-first (see the group-log entry above); groups whose membership events predate this producer have an empty log and still need the manual re-pair path once. Wedge-proofing (cross-review P1-1): apply errors are classified by FAULT DOMAIN (surfaced as the structured `X0xdError::ApplyRejected`): every deterministic record-fault 4xx (400/403/404/405/411/413/415/422/...) is a traced skip-and-advance so one poison or stale record can never wedge recovery, while environment-faults (401/407 auth, 431 headers, 408/429 transient) and everything outside 4xx stay retryable errors with the cursor held -- a wrong Err is a visible wedge, a wrong skip is silent unapplied loss. Known Lane B blockers, tracked in `log_source.rs`/`group_log.rs` doc-comments: log-head-eviction floor adoption, (relay,group)-keyed cursors for primary flips, durable cursors (own-JoinResult replay), bounded log_fetch accumulation, optional payload sealing, and the relay-cap(1.5 MiB)/daemon-body-limit(1 MiB) incoherence (an oversized Welcome deposits at the relay but 413s on apply and skips to cold -- bound the producer payload or raise the daemon limit).

- Private-group **decrypt works without prior per-sender DM pairing** (Option B): `Endpoint::receive_private_group_envelope` (`crates/fetchit-chat/src/messages.rs`) ML-DSA-verifies the sender against their stored card, then x0xd `/secure/decrypt`. An un-paired sender's signing key is resolved on the fly from the relay pair-record (`crate::pair::fetch_pair_record_by_id`; `verify_pair_record` in `crates/fetchit-relay-proto/src/pair_record.rs` binds `agent_id == SHA-256(domain || ml_dsa_pubkey)`, so a hostile relay cannot forge it) and persisted via `StoredContactCard::save_imported` (merge-floor, never downgrades a fuller card). ## Chat -- linked-device DM fanout (M6.3)

- **A DM fans out to a contact's linked devices**: to an M6 contact (whose imported card carried an x0x `user_id`), `Endpoint::send` resolves their signed device list and seals one copy per device -- every linked device receives it, sharing one `message_id` for receive-side dedup, with no primary-device-online dependency (model A receive-fanout, complementary to the future M6.6 devices-group, not a substitute). `fanout_targets` -> `fanout_targets_from_record` (`crates/fetchit-chat/src/messages.rs`). A sibling device discovered only from the signed record (never imported as a contact, so no stored card) is bootstrapped straight from its user-signed `DeviceEntryV4` via `bootstrap_from_device` (record KEM); `bootstrap_conversation` (stored card) is the single-device fallback. Delivery is best-effort per device (one device's failure never aborts the rest), and the outbound `HistoryEntry` is anchored once on the `to`-agent conversation, so a multi-device contact stays exactly one sidebar thread.
- **Confidentiality gate (anti-redirection)**: `fanout_targets_from_record` trusts the resolved device list ONLY when `to` is one of the listed devices, else single-device fallback. The card `user_id` is only an AGENT-asserted claim (the x0x `AgentCard` carries no user-signed cert; `verify_card_extension` covers only the fetchit KEM/agent extension), so without the gate a spoofed card (`agent=Mallory, user_id=Victim`) would seal the DM to the victim's devices. The `PairRecordV4` USER signature covers each device's `agent_id_hex` (`pair_record_v4_signing_input`, `crates/fetchit-relay-proto/src/pair_record.rs`), so `to`-in-devices proves the account signed `to` as its own. Trust model in `crates/fetchit-chat/SECURITY.md` caveat 10.
- **Contact device-list read side**: `contact_user_id_hex` surfaces the peer's account root from their stored card; `resolve_pair_record_v4` GETs + verifies their signed device list from the contact's own relay with strictly-monotonic anti-rollback against a per-contact cache (`crates/fetchit-chat/src/pair_record_v4.rs`); a newer revision that revoked a device cancels that device's pending outbox sends (`removed_device_agents` + `OutboxStore::drop_bubbles_for_peers`, `crates/fetchit-chat/src/outbox/store.rs`).

## Chat -- proactive pair-record push (M6.7 send/receive)

- **A device-set change pushes the re-signed roster to active contacts** instead of making them wait to re-resolve: `Client::push_pair_record_to_active_contacts` (`crates/fetchit-chat/src/client.rs`) enumerates the distinct active peer devices across every cached conversation (`pair_record_push_recipients` over `Conversation::fanout_devices`, which drops our own device + revoked devices; cross-conversation duplicates collapsed) and sends each one an unsealed `PairRecordPush`. The push rides an `OutboundKind::Dm`-shaped envelope whose transit `kind` stays `EnvelopeKind::PairRecordPush`, so the relay forwards it (LAN drops it) and the receiver re-discriminates on `transit.kind`. Best-effort per recipient; the return count is the recipients the router accepted.
- **Receive is authority-gated, not sender-trusted**: the push is public + self-signed, so `Client::dispatch_inbound_pair_record_push` (`crates/fetchit-chat/src/client.rs`) ignores a push from a non-contact (`contact_user_id_hex` must resolve the sender's x0x `user_id`), then `accept_pushed_pair_record_v4` (`crates/fetchit-chat/src/pair_record_v4.rs`) accepts ONLY when `record.user_id_hex == expected && verify_pair_record_v4(record).is_ok() && record.revision > last_seen` (the record's own ML-DSA-65 user signature + strict anti-rollback are the sole authority). On accept over an existing record, the devices the new revision revoked have their pending outbox sends cancelled (`removed_device_agents` + `OutboxStore::drop_bubbles_for_peers`), mirroring the M6.3 resolve cleanup. The wire is unsealed by design (`crates/fetchit-relay-proto/src/pair_record_push.rs`, WIRE_VERSION 3). NOTE: the automatic trigger on a LOCAL device-set change (the revoke orchestration that calls `revoke_device_and_publish` -> devices-group `DevicesGroupSink::remove_device` -> this push) converges with the M6.6 devices-group and is not yet wired.

## Chat -- cross-NAT group-join (engine A)

- **Gossip-independent PQ TreeKEM group-join over the relay** (engine A): a NAT'd joiner converges into a group whose owner is also NAT'd, with no gossip/mDNS -- the FALLBACK for the dual-NAT corner where gossip can't reach a NAT'd owner (native x0x groups + gossip is the PRIMARY group path; gossip ships ON). Forward path -- the joiner's signed `member_joined` is bridged sealed to the owner, which applies it through `apply_metadata_event` (full ML-DSA + single-use invite + inviter gate) and publishes the authoritative `MemberAdded` -- `crates/fetchit-chat/src/client.rs:2170` (`join_group_bridged`), `crates/fetchit-chat/src/client.rs:1871` (`dispatch_inbound_bridge` forward arm), `crates/x0xd-client/src/secure.rs:574` (`apply_metadata_event`).
- Reverse path -- the owner bridges the `MemberAdded` back sealed; the joiner self-detects it and applies it locally so its TreeKEM membership poll resolves -- `crates/fetchit-chat/src/client.rs:2012` (`reply_to_bridged_join`), `crates/fetchit-chat/src/groups/join_bridge.rs:92` (`member_added_self_target`) + `:77` (`stable_group_id_from_member_joined`), `crates/x0xd-client/src/secure.rs:631` (`apply_join_result`). The joiner daemon gates the applied event to MemberAdded-only, `member == self`, `sender == creator`, and re-verifies the signed commit (wiremock-tested 200/409/403 in `secure.rs`).

## Chat -- who-is-who (per-identity color + sealed sender name)

- Per-identity **bubble color + sender-name label** so group senders are scannable at a glance: a deterministic hue index off `agent_id` drives the avatar gradient, the bubble accent stripe, and the sender-name color as one identity -- `apps/fetchit-desktop/src/chat/avatarColor.ts` (`identityIndex` %8 + `avatarGradientClass` / `bubbleIdentityClass` / `senderIdentityClass`), rendered in `bubble.ts` + `conversation.ts` (`groupAttribution`). Android mirrors the same index in `IdentityColor.kt`.

## Fediverse bridge (M4 / M5.1)

- HTTP Signatures use **classical RSA-2048 + PKCS#1 v1.5 + SHA-256** (`rsa-v1_5-sha256`), NOT Ed25519 and NOT post-quantum -- `crates/fetchit-fedi/src/signature.rs`. The PQ binding is the ML-DSA-65 attestation in the Actor JSON-LD, not the per-POST signature. Crypto source of truth: `docs/honest-claims-crypto.md` §3.
- **One-tap mint (minimal profile)**: a fresh identity with no etch/it-published profile can still mint a fediverse handle. When the relay has no profile-index record (404 / tombstoned), `Client::mint_and_register_actor` (`crates/fetchit-chat/src/client.rs`) publishes a minimal handle-only record via `Client::publish_minimal_profile` -> `pair::sign_minimal_index_record` (`crates/fetchit-chat/src/pair.rs`): a self-signed `ProfileIndexRecord` carrying the reserved `pair::MINIMAL_PROFILE_ADDR` sentinel (not the all-zeros tombstone), POSTed to `{relay}/v1/profile`, no wallet / no Autonomi write. Only a genuine 404/tombstone triggers it -- an existing real profile is used and never clobbered; a transient relay error propagates. Both shells route through this one path: desktop `fediverse_mint` (`apps/fetchit-desktop/src-tauri/src/fediverse.rs`), the mobile FFI `fediMint` (no FFI API change -- one-tap on a `.so` rebuild). The rich profile stays an optional etch/it upgrade (same-`agent_id`, not a takeover).
- **Mint outcomes are classified, and a name conflict is terminal** (`#331`): the bridge answers `POST /actors` with `201` on a first registration, `200` when the SAME agent id re-registers (idempotent update -- how an attestation refresh self-heals), and `409` ONLY when the handle row belongs to a DIFFERENT agent id (`crates/fetchit-bridge-server/src/store.rs` `register_actor`, surfaced in `routes/actors.rs`). `fedi_identity::register_or_update_actor` maps those onto `fedi_mint_state::RegistrationState` -- `Registered` / `NameTaken` (terminal) / `Transient { reason }` (retry armed) -- and `Client::mint_and_register_actor` persists the last outcome to `<root>/fedi/mint_state.json` (`crates/fetchit-chat/src/fedi_mint_state.rs`), so a conflict survives a restart instead of decaying into an eternal "registration pending". `Client::ensure_actor_v2_and_register` short-circuits on a recorded `NameTaken` for that handle (the automatic self-heal loop stops; an explicit user-driven mint always re-asks the directory), and a conflict discards the identity the failed mint just created so it cannot shadow the name the user picks instead. A refused handle also stops being presented as the active `@name`: `fedi_mint_state::active_handle` (which `ChatClient::fedi_actor_status` now reads) prefers the handle the directory accepted and never returns one it refused, so the shells' "mint a handle" affordance -- gated on that being `None` -- comes back instead of the app claiming a name the directory serves for someone else. Shells read `MintRegistrationFfi` (`Registered` / `NameTaken { handle }` / `Retrying { reason }`) plus `ChatClient::fedi_mint_state` for the cold-start read; Android's mint dialog keeps itself open with an inline "already taken" error and reopens seeded with the failing name (`apps/fetchit-android/app/src/main/java/io/etchit/fetchit/chat/FediMintFeedback.kt`, `ChatModeView.kt`). Releasing an orphaned handle is NOT covered -- that is `#332`.
- **Own profile picture, hosted by our own bridge**: the user picks a photo; the shell decodes it, centre-crops, downscales to 512px and RE-ENCODES it as JPEG before anything leaves the device (`apps/fetchit-android/app/src/main/java/io/etchit/fetchit/chat/ProfilePicture.kt`) -- the re-encode is the privacy step, since a camera JPEG's EXIF routinely carries GPS. `Client::set_fedi_avatar` (`crates/fetchit-chat/src/fedi_self_avatar.rs`) uploads the bytes to `POST /actors/:handle/avatar` under `bridge-auth-v1`, records the resulting `icon` URL on the actor vault, re-registers the document so Mastodon-class consumers show the picture, and pins a local copy in the avatar cache; `clear_fedi_avatar` unwinds all four. The bridge stores the bytes verbatim in two nullable `actors` columns (`crates/fetchit-bridge-server/src/store_avatar.rs`, added by an idempotent `ALTER TABLE` so the deployed database upgrades in place) and serves them from the public `GET /actors/:handle/avatar` with the stored `Content-Type` and `X-Content-Type-Options: nosniff` (`routes/avatar.rs`). Uploads are gated on BOTH a content-type allowlist (jpeg/png/webp; no SVG, no GIF) and the matching file magic (`fetchit_fedi::avatar::magic_matches_content_type`) -- without the magic check a registered user could park arbitrary content under `etchit.io` -- plus a 512 KiB body cap and a per-IP limiter on the write verbs only. Nothing server-side ever decodes the image. The local copy is marked `pinned` in `fetchit_chat::fedi_avatar` and skipped by eviction: every other cache entry can be re-fetched from a public URL, but the private (LIT) surfaces that draw the self badge may never issue that fetch. FFI: `ChatClient::fedi_set_avatar` / `fedi_clear_avatar` / `fedi_self_avatar` (cache-only).

- **Profile sheet on any account**: `Client::fetch_fedi_profile` (`crates/fetchit-chat/src/fedi_profile.rs`) turns one actor document into `{actor_url, label, display_name, bio_text, icon_url}`. It accepts `@user@host`, `user@host`, and actor-URL targets so a tapped author chip, a tapped @-mention, and a typed handle all take one path; handle forms go through the denylist-gated mention resolve, URLs through `Client::gate_actor_url`. `RemoteActor` now decodes `name` / `summary` (`crates/fetchit-fedi/src/lookup.rs`) and the bio is reduced with `fetchit_fedi::text::html_to_text` engine-side, so no remote markup crosses the FFI. FFI: `fediProfile`. Deliberately NOT gated on a minted handle -- reading a public profile is a read; the sheet's ACTIONS (follow, message) gate shell-side. Android: `ChatModeView.showFediProfileSheet`, reached from the feed author chip and from ClickableSpans over each mention (`FeedMentionSpans.kt` matches a Mention tag back onto the reduced plain text by full handle, then by local part alone -- all a Mastodon-family server's markup reduces to).
- **Mentions survive the read path**: `RemotePost.mentions` carries the Note's AS2 `Mention` tags (`{name, href}`, capped at 32/post) through `FediFeedPost` and `FediPostFfi` to the shells, which previously received only the post's text and so could not make an @-mention tappable at all.
- **Report an account to moderators**: `Client::report_target` / `report_actor_url` (`crates/fetchit-chat/src/report.rs`) POST a `fetchit_trust_types::Report` to `{trust base}/report` -- the queue `crates/fetchit-trust/src/server.rs:submit_report` has served since M3 with **zero client callers** until now. The target is built through `TargetIdentity::try_new`, so the reviewer sees the exact canonical form a denylist entry would carry (lowercased, https-only, no userinfo/query/fragment, one trailing slash stripped) and a promoted report matches the gate that reads it. Reporter = this device's `local_agent_id_hex` (anonymous from a REST-only client rather than refused). Comment capped at `MAX_COMMENT_LEN` (2000); `attached_excerpt` is ALWAYS `None` -- disclosing plaintext is a separate explicit choice, never a side effect. Base resolves via `FETCHIT_DENYLIST_URL` else the compiled-in `https://trust.etchit.io/v1`, so a report and the list it may join can never diverge. Reporting is NOT blocking (the shells' local block store is the instant remedy). FFI: `fediReport(actorUrl, reason, comment)`; the `snake_case` reason vocabulary is parsed engine-side by `report::parse_report_kind` so no shell needs a trust-types dep. Android: "report…" on the profile sheet's action stack and both following-row overflow menus, opening a radio-list dialog (`FediReportReasons.kt` -- the six offered kinds, `other` deliberately withheld as unactionable) with an optional comment; honest sent/failed toast either way.
- **The read feed is denylist-gated per account**: `fetch_fedi_feed` (`crates/fetchit-chat/src/fedi_feed.rs`) runs `Client::gate_actor_url` on each followed account BEFORE `fetch_remote_actor`, so a blocked account's server receives no request at all rather than being fetched and then filtered out. The gate has to run per refresh, not only at follow time: the follow row lives at the bridge and the block lives at the trust service, so a row routinely outlives the block. Shared body is `public::check_optional_actor_url_denylist`, which fails open with no consumer installed and fails CLOSED on a URL that will not canonicalize.
- **The bridge enforces the denylist on inbound federation**: `crates/fetchit-bridge-server` had no `fetchit-trust*` dependency at all despite being the binary that terminates real federation traffic. `POST /actors/:handle/inbox` now gates the signature-verified sender (`routes/inbox.rs`, after `verify_inbound_signature`, before any dispatch arm and therefore before every store write) via `denylist::is_blocked_actor`, answering `403` -- the same observable status the relay-server's `DropReason::Denylisted` produces -- and bumping the unlabelled `fetchit_bridge_inbox_denylisted_total` counter. `denylist::install` reuses `fetchit_trust_client::DenylistConsumer` as-is (cache hydrated synchronously, poll loop detached), wired in `main.rs` inside the runtime. On by default against production; `FETCHIT_BRIDGE_DENYLIST_URL` set EMPTY is the only disable (how the hermetic tests run) and `FETCHIT_BRIDGE_DENYLIST_CACHE` is the optional offline snapshot. An end-to-end 403 is not hermetically reachable (verification needs an actor document the SSRF guard will not pull from loopback), so `tests/inbox_denylist.rs` pins the wiring + counter and `src/denylist.rs` unit-tests the decision.
- **Autonomi addresses in outbound posts are links, not dead text**: `markdown_body_to_html` (`crates/fetchit-fedi/src/activity.rs`) escapes as before, then wraps each address in `<a href="https://etchit.io/a/#<hex>">` via `linkify_autonomi_addresses` -- the funnel from a Mastodon timeline into fetch>it. Grammar mirrors the Android detector (`AutonomiRefs.kt`): optional `autonomi://`, optional `0x`, exactly 64 hex, no `[0-9A-Za-z_]` adjacent either side, so a 65-hex run never linkifies. The anchor is SYNTHESISED from a hex-only match (never passed through from the body), so the XSS-safe-by-construction claim holds, and the anchor TEXT is the matched token verbatim so `text::html_to_text` round-trips it back for fetch>it clients that grow their own content card.
- **Like / unlike a post**: `fetchit_fedi::activity::build_like` / `build_undo_like` mirror the `Follow` builders; `Client::like_fedi_post` / `unlike_fedi_post` (`crates/fetchit-chat/src/fedi_like.rs`) resolve the author (denylist-gated), sign, and deliver to their inbox. Liked-state is device state in a sealed, bounded store (`<root>/fedi/likes/<handle>.json.enc`, oldest-first eviction past 2000) joined against the feed as `FediPostFfi.liked`. The activity id is derived from the post URL, so a re-send after a failed delivery is idempotent remotely and an unlike works with no local record. Liking a denylisted author errors before anything is recorded; unliking one is always allowed locally, because withdrawing an interaction must stay possible. **No like COUNTS** -- there is no cheap ActivityPub source for a total, so v1 renders the toggle and no number. FFI: `fediLike` / `fediUnlike`; Android: heart on the feed row, optimistic through `FeedStore.setLiked` with a revert on FFI error.
- **Read the conversation under a post, with ZERO server-side storage**: a reply lives in the REPLIER's outbox on THEIR server, so the feed's per-account outbox walk can never see one -- the feed showed posts and no replies, which reads as a noticeboard rather than a room. `fetchit_fedi::lookup::fetch_thread_replies` (`crates/fetchit-fedi/src/lookup.rs`) pulls the Note's own `replies` Collection on demand, the same shape of device-side pull the feed already is: nothing is added to `fetchit-bridge-server` or `fetchit-relay-server`, and nothing is persisted on the device either. Shapes handled: `replies` absent, a bare URL to fetch, an inline `Collection` with `first` (inline or URL), a `CollectionPage`'s `items` OR `orderedItems`, entries that are bare URI strings / bare `Note`s / `Create`-wrapped Notes / id-only stubs, and `next` pagination. Caps: `MAX_THREAD_REPLY_PAGES` = 2 (Mastodon's page 1 is the author's own self-replies and everybody else's live behind `next?only_other_accounts=true`, so one page would show an empty room for almost every real thread), `MAX_THREAD_REPLY_FETCHES` = 20 (Mastodon reduces non-local replies to bare URIs, so most entries cost their own GET), `MAX_THREAD_REPLIES` = 50, and `THREAD_FETCH_BUDGET` = 20s of wall clock across the lot, because `ACTOR_FETCH_TIMEOUT` alone would let twenty slow-but-legal answers hold a view for minutes. Two hardening rules the feed path did not need: a `first`/`next` that leaves the origin host is refused before any socket opens, and a reply whose `attributedTo` names an actor on a different host than the document that served it is DROPPED -- without that, any instance could put words in any account's mouth by listing them in its own thread. `fetchit_chat::fedi_replies::Client::fetch_fedi_thread` gates each reply author through `check_optional_actor_url_denylist` (fail-open, exactly as the feed), reduces bodies with `fetchit_fedi::text`, and joins the liked-set. No `author_name` on a reply: the name lives in the author's actor document and that would be one more fetch per distinct replier. FFI: `fediThreadReplies(objectUrl) -> FediThreadRepliesFfi { replies, repliesServed }` -- a bare list could not carry the one distinction the view needs, since "nobody has replied" and "this server publishes no replies collection" are different facts. Not gated on a minted handle (reading a public conversation is a read). Android: `ChatModeView.bindPostThreadScreen` behind a 💬 control and a body tap (`BodyTapMovementMethod` -- `TextView` fires `View`'s click BEFORE the movement method, so an `OnClickListener` would steal @-mention and `autonomi://` span taps), with four distinct states from `FediThreadRows.state`.
- **A reply actually threads**: `inReplyTo` names the parent STATUS, and `PublicPost` carried only the replied-to ACTOR url -- so every reply this project has ever sent named a Person there, was delivered, and hung under nothing. `PublicPost` now carries `reply_to_actor_url` (addressing + denylist gate) and `reply_to_object_url` (`inReplyTo`) as separate fields, and `build_create_note` reads the object url and nothing else; a caller with only an actor url sends a top-level post rather than a malformed `inReplyTo`. FFI: `fediPublish(bodyMd, replyToActorUrl, replyToObjectUrl)`; desktop `fediverse_publish` gained the matching argument and passes `null` (its composer knows only the author).

## Chat -- inline photo attachments (E2EE, DM only)

- **A photo rides INSIDE the sealed message payload**, so it is end-to-end encrypted exactly like the text and needs no new envelope kind: `fetchit_chat::attachment::Attachment { mime, width, height, bytes_b64 }` on `MessagePayload` / `HistoryEntry` (`crates/fetchit-chat/src/attachment.rs`, `conversation/types.rs`), capped at `MAX_ATTACHMENT_BYTES` (256 `KiB` raw, ~4x under the relay's 1.5 `MiB` envelope limit) with a raster-only MIME allowlist -- `image/svg+xml` is refused because SVG can carry script. Validated on BOTH sides: `build_message_outbox` refuses a bad one before sealing, and `conversation/inbound.rs` drops a hostile inbound one to `None` while still rendering the message.
- **DM only.** A private-group frame is sealed as `encode_group_plaintext(sender_name, body, seq)`, which has no attachment field, so both shells HIDE the attach affordance on group and fediverse threads rather than promise a send the wire would drop (`conversation.ts` `setAttachVisible`, `ChatModeView.hideAttachAffordance`).
- **FFI both directions, raw bytes**: `ChatAttachmentFfi` (`crates/fetchit-ffi/src/attachment_ffi.rs`) mirrors the engine record with RAW bytes -- base64 is applied and stripped at the boundary, so Kotlin only handles what a decoder takes. Send: the optional parameter on `ChatClient::enqueue_dm` / `send_dm`; receive: `ChatEventFfi::Dm.attachment` and `ChatHistoryMessageFfi.attachment`. An attachment that fails validation maps to `None` on the way up, never to a bad record.
- **Android send** (`chat/ChatImageAttachment.kt`): the DM composer's attach button opens the permission-free `PickVisualMedia` picker; the photo is decoded bounded + subsampled, scaled KEEPING ITS ASPECT RATIO (a shared photo is the content, unlike a centre-cropped avatar) and RE-ENCODED as JPEG down an (edge, quality) ladder until it fits the cap. The re-encode is the privacy step: a camera JPEG's EXIF routinely carries GPS. A picture that fits no rung is refused with the honest steer to the `autonomi://` share path. A staged image shows as a chip with a remove X, and send stays live with an empty box while one is staged (an image alone is a message).
- **Android render**: inbound AND outbound bubbles draw the picture above the text, sized from the carried width/height BEFORE the decode so the thread does not jump, decoded off the main thread and cached (`ChatImageAttachment.Thumbs`); a tap opens it full screen (`dialog_chat_image.xml`).
- **The sender's own copy is durable.** The engine's outbox bubble carries the image itself (`OutboxBubble::attachment`, surfaced as `OutboxBubbleFfi.attachment`), so a sent photo reloads from the vault and still draws in the sender's thread after a restart, and an engine-driven RESEND re-sends the picture instead of a text-only reduction of the message (`Endpoint::resend_dm_bubble`). `ConversationStore.stageOutboundAttachment` survives only as an optimistic-render accelerator for a bubble that has no image of its own. `mergeHistory` treats the persisted transcript as the durable truth: a hydrated duplicate whose image the shown copy lacks patches it in, rather than being dropped wholesale.
- **Retained images are bounded** (`outbox::ATTACHMENT_BUBBLE_CAP`, 16): a bubble releases its bytes the moment it goes terminal -- silently at `delivered` (the transcript holds a copy) and flagged `attachment_dropped` at `failed` (nothing else does, so the shell renders an explicit "photo not kept" note). Past the cap an image send is REFUSED (`ChatError::OutboxAttachmentsFull`) rather than accepted without its picture.
